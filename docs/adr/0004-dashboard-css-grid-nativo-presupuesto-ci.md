# Dashboard: CSS Grid nativo con enteros + presupuesto de rendimiento en CI

Decidimos que el layout del dashboard usa CSS Grid nativo con geometría en enteros (12×10), sin JS en el loop de layout, y que el resize fluido se protege con un presupuesto de rendimiento medido por `npm run test:perf` en CI.

El motivo es que el modelo anterior posicionaba widgets con porcentajes flotantes (`xPercent`, `yPercent`, `wPercent`, `hPercent`) y resolvía la geometría en JS con `useDashGrid` (interact.js + ResizeObserver + `applyGapToPixel`), re-ejecutando layout por cada cambio de tamaño. Eso hacía que maximizar la ventana o arrastrar su borde produjera jank visible: el trabajo de layout corría en JS en el loop de resize. Con CSS Grid nativo, el navegador reparte `repeat(12, 1fr)` / `repeat(10, 1fr)` y posiciona cada widget con `grid-column` / `grid-row` en enteros; el resize no dispara trabajo de layout desde JS, solo el layout nativo del browser.

El presupuesto de rendimiento protege la decisión: `tests/perf/perf.spec.ts` (Playwright, Chromium, aislado y determinista) anima el viewport de 800×600 a 1920×1080 con el IPC de Tauri stubeado y exige que los long tasks > 50ms, el gap máximo de frame y el settle se mantengan dentro de umbrales calibrados sobre la línea base del dashboard completo (fixture sin overlaps) en `tests/perf/perf-constants.mjs`. La línea base (14 long tasks > 50ms, gap ~233ms, settle ~106ms) refleja el layout nativo de los widgets pesados (calendario anual y heatmap de hábitos); el presupuesto suma headroom para CI (20 long tasks, gap <300ms, settle <350ms). La contención (`contain: layout paint`), el recompute discreto de los widgets pesados (year-calendar, heatmap) y la animación FLIP transform-only completan el modelo: el trabajo costoso queda fuera del loop de resize.

La contrapartida es que un ítem que quede fuera del presupuesto rompe `test:perf`; eso es deliberado: un cambio que toque el dashboard o la grilla debe mantener el presupuesto (ver Definition of Done en AGENTS.md). Widgets con layout interno pesado (calendario anual, heatmap de hábitos) siguen siendo los puntos calientes medidos; su reescritura (virtualización) queda como trabajo futuro fuera de este ADR.
